# Decisions and open questions

## Confirmed baseline

- The proposed stack is PHP, HTML5, CSS3, JavaScript, and MySQL/MariaDB; XAMPP is proposed. Keep the stack unless a change is explained and approved.
- Bevy is the registration platform; organizers are expected to provide participant data.
- A valid first check-in records attendance and queues a separate initial name-tag print job. Duplicate check-in is prevented, and queue failure does not undo attendance. Physical printer dispatch is still unconfigured.
- The user wants production deployment to use Supabase and has agreed to the target print flow where a separate printer computer retrieves queued jobs and prints them without a browser dialog. The PHP application host, database migration, printer computer/service, and approved print layout are still unresolved; see [printing and deployment](printing-deployment.md).
- Certificates are a separate workflow; only checked-in participants are eligible. Admins queue certificate jobs manually from the Certificates tab. Check-in does not automatically queue a certificate; queue actions do not imply physical printer dispatch.
- Do not invent participant data, QR conventions, official branding, or templates. Review the real schema and participant data before changing database design.
- The registration team aligns shared table and column names with the booth team's supplied `db_gdgevents.sql`, adding registration-specific fields/tables where needed. The imported `db_gdgevents` database was inspected read-only and includes `attendees.nickname` and the registration tables. PHP database queries now use `attendees`; `.env` points to `db_gdgevents`. No database migration or existing data change was made during this code alignment.

## User answers recorded on 2026-10-21

- The supplied SQL is an initial schema, not final; `attendees_new` is intended to be the attendee table.
- QR is believed to be the ticket number, but this is unverified. Ticket numbers are expected to be globally unique.
- One person may register for multiple events, but may have only one ticket per event.
- Admin enters event details; there is no fixed limit on the number of events (clarified 2026-10-24).
- Organizer export is expected to contain a nickname; nickname is used on name tags and full name on certificates. The actual export has not been received.
- Expected export data fields are ticket number/QR, first name, last name, email, and nickname; actual headers, format, encoding, and QR decoding remain unverified.
- Duplicate registrations/imports should not create another registration; skip and report an existing registration.
- Email is stated to be guaranteed and unique; verify against the real export before enforcing a database constraint.
- Admin searches by name and QR. Staff may see full name and QR during check-in; confirm whether Staff may also search by name.
- Admin may correct mistaken check-ins; corrections should be recorded. Staff cannot correct them.
- Dashboards should show check-in statistics.
- The first Admin is created through the local setup flow. An Admin invites later Admin/Staff accounts in Settings; the recipient chooses a password through a one-use activation link. Admin password changes require the current password. Admin-generated one-use password-reset links are available for other accounts; automatic email and self-service recovery remain unconfigured.
- Admin configures name-tag dimensions and uploads a predesigned layout. Printing should start automatically after successful check-in.
- Admin uploads the organizer-provided name-tag design, sets its overall width and height, then positions and resizes one attendee-name area on a preview. The Admin can also set the name font size, family, alignment, and color. The configured layout is reused for each attendee; the first successful check-in queues that attendee's tag for automatic printing, and Admin can also request initial prints/reprints from Name Tags. Coordinates are proposed in millimeters from the template's top-left. Actual font values, overflow behavior, and accepted file formats remain open.
- Admin authorizes and records name-tag reprints. Certificate eligibility requires successful check-in; organizers supply certificate design/template, full name is printed, and Admin handles/records issuance or reprints.
- A GDG logo asset has been supplied at `public/assets/images/gdg-logo.svg`; additional brand guidance may still be provided.
- Staff check-in should work on laptop and phone. Deployment is local for now.

## Open questions and dependencies

1. **Participant export:** What file type, encoding, exact columns, and sample rows will organizers supply? Confirm how QR/ticket values appear and validate email uniqueness.
2. **Live database/environment:** Does the initial dump match any database currently installed? What PHP and MariaDB/MySQL versions are available?
3. **Staff lookup/privacy:** May Staff search by name or only scan/enter QR? Is showing the QR/ticket identifier necessary after lookup?
4. **Corrections:** What audit details are required for an Admin correction (reason, old/new state, timestamp, acting account)?
5. **Printing:** Which computer/OS will run the local print service, and what implementation can be installed there? What are the tag dimensions and approved layout file? What does "stop" mean for printing (cancel a queued job, disable future prints, or another action)?
6. **Certificates:** What does "stop" mean for certificates (cancel queued printing, revoke an issued certificate, or another action)? What template format will be provided?
7. **Accounts:** Should the app add automatic email delivery for Admin-generated setup/reset links, and is self-service password recovery needed?
8. **Deployment/device:** Which PHP-capable host will run the MVC application, and will Supabase Postgres replace the current MySQL/MariaDB database in production? How will phones reach the deployed site? Camera access may depend on secure browser and network setup.
9. **Team policy:** Approve or revise the proposed Admin/Staff permission matrix above.
10. **Branding:** The GDG logo file is available; confirm any remaining brand guidance.

## Not selected yet

- QR scanning library.
- Supabase/PostgreSQL production integration and PHP application hosting; the current development database remains MySQL/MariaDB.
- Exact local print-service implementation and printer computer/OS; the target is a separate service that sends queued jobs without a browser dialog.
- Exact schema and import mapping; the CSV has not been supplied.
- Certificate artwork file formats, approved font choices/defaults and overflow behavior, and print-service delivery details.
- Final UI tokens and official brand assets.
